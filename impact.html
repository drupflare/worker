Impact

What drupflare costs to run, in money, electricity, carbon and water, and how far each figure can be trusted. The page leads with energy, then gives the models and measurements behind it, then carbon, water and price.

Production Baseline

Enterprise Drupal runs oversupplied. Teams that put performance ahead of cost run high-availability, multi-region deployments sized for peak, and those nodes draw their idle power around the clock. The baseline is three regions, a high-availability web pair and database pair in each (12 nodes), 4-vCPU nodes sized at 15% utilisation. Each node owns its vCPUs' share of a 640-thread host drawing 135 W idle and 711 W at full load, at the 1.54 colocation PUE.

That deployment draws 224 kWh a year while idle-dominated. drupflare serving the same site at 1 million views a month draws 18.3 Wh a year, a saving of 99.9919%.

The node count, the vCPU per node and the utilisation are modelled, because no source sizes a production node. The topology follows Acquia's high-availability design, which spreads a site over several availability zones of one region [4], and the AWS reference architecture for Drupal, whose subnets sit in two or three zones [5]. A VPS vCPU is a hardware thread, so a node owns its vCPUs over 640 of the host.

drupflare's busy core is a physical core, because each Workers isolate thread runs on one. Its energy is CPU time on the traffic mix at 2.22 W a core, charged under Watts For A Busy Core, with logged-in views at the compiled-plan cost. Energy Per View has the mix and the plan.

The saving is the idle term. These nodes are provisioned for peak, so almost all of their energy is spent waiting. A site that sleeps between requests holds no compute and spends energy only while a view, a render or a cold boot executes. A site kept warm also pays for its warming and holds its memory, which Operating States prices. Per request the two runtimes are at parity, as the measurements below show, so none of this comes from PHP running faster.

Every row saves more than 99.5% against production and more than 90% against the worst case. The compound bound adds the full object budget, the warming CPU at the billed wall time and five cold encounters a day. It is not a state a site sits in: an object that stays warm does not meet idle cold boots, so those encounters come from outside causes such as an eviction, a deploy or a replaced isolate.

  • Cold encounters: a sensitivity with no measured rate. A cold encounter is a boot plus a first render with the cache bins empty, 1,264 ms plus 2,127 ms of CPU, both measured. How many a site meets is the number of editor sessions that find the object cold, and cached anonymous views never boot PHP. coldOfTraffic is the instrument for the rate and no deployed site has reported a reading, so the headline carries none. At 10,000 views, five a day moves the saving from 99.9998% to 99.9978%.
  • Warming CPU: bounded, not read. A firing bills 23.3 ms of wall time (n=116 on two deployed objects) and its CPU time has not been read. The first warm row charges all of the wall time as CPU, an upper bound; the second charges a tenth.
  • Memory: the memory rows charge a kept-warm object for the memory it holds, as accounting bounds. A booted interpreter takes about 165 to 175 MiB of an object's 195 MiB budget, measured on a paid object with a build whose linear memory started at 80 MiB; the shipping build starts at 64 MiB, which can only lower it. A large site such as farmOS holds 196 to 201 MB warm. The first row charges 170 MiB and the second the full 195 MiB, the limit at which the platform resets an object and not a measured footprint for every site. The memory of a warm object is a plateau: an interpreter's linear memory is reused after a drop and keeps the largest size any interpreter reached, so a kept-warm object holds its high-water mark until its incarnation ends. 170 MiB of the 384 GiB host is 0.0432%, charged at the host's 135 W idle draw and the 1.15 PUE: 589 Wh a year. That assumes the host is provisioned for memory. Cloudflare does not publish how objects are packed, and if the memory sits in DRAM that is powered anyway the marginal charge is zero. A site that sleeps ends its incarnation after ten idle seconds, and a cached page is served without booting the interpreter, so it holds the interpreter's memory only while it renders. The sleeping rows carry no memory charge.

Where The Saving Comes From

The saving has two sources, and neither depends on PHP running faster.

  • Idle capacity: conventional multi-tenant hosting for small sites is memory-bound. Packed at 1,000 sites of 1 GB on a 1.5 TB two-socket host, the fleet runs its processors near zero and draws about 1,826 kWh a year at 10,000 views a site, 1,822 of it idle (99.8%). It buys processors it never uses and powers them continuously. A sleeping site consumes energy only while it executes.
  • Invalidation: a page store invalidates on content change, while a CDN expires on a clock. cfw_page carries a stale_at column set when a save invalidates a tag, so a cached page survives until the content behind it changes. A CDN in front of a conventional origin re-renders every path, at every edge location, once per TTL whether or not anything changed. Modelled at 20 million views per site per month with five saves a day, that is 28.34% of requests rendering for a CDN and origin against 0.004% for drupflare, 186,371 renders a day against 25. A per-location cache miss reaches the page store, which answers without PHP.

The Render Fraction

derived (modelled). Models of edge-cached hosting often assume a flat share of requests that render. The share depends on traffic:

renders = sum over paths of min(requests, window / TTL)   per path, per edge location
          + saves x pages invalidated per save

The floor does not depend on traffic, so the fraction falls as traffic rises. It is a property of a site's content-to-traffic ratio, and a single number for a whole fleet is wrong in both directions. For a CDN and origin a common 1% assumption is first reached at roughly 723 million views per site per month, far above the range these models cover.

drupflare has no TTL term and no location term. Its renders are saves times the pages each save invalidates, 5 for an ordinary node save, so at five saves a day a site renders about 25 pages a day whatever its traffic. The fraction is 7.6% at 10,000 views a month, 1% at about 76,000 and 0.004% at 20 million. A save the main menu references invalidates every cached page, 34 on the measured site, and is the pessimistic arm.

For a CDN and origin the edge-location count is the largest term: at 20 million views it spans 4.38% at one location to 62.91% at fifty. A measurement taken from a single source address reads a floor, because a one-address generator drives one edge location while real visitors spread across many.

scripts/measure/render-fraction.ts computes it, with each input named as measured or modelled.

Energy Per Request

measured. RAPL package and core domains on a bare-metal AMD Ryzen 9 9900X, load generated off-box, arms rotated per round, idle subtracted, n=5 per rung with no sample discarded. Both stacks run on the same machine against the same counter in one interleaved run: the shipped docker/vps.yml (nginx plus PHP 8.5 FPM with opcache and JIT) and drupflare under standalone workerd serve, each capped at 3 CPUs by cgroup.

The cap is the VPS stack's total, vps-php at 2 plus vps-web at 1. It is read back from the running containers as a cpu.max of 200000 100000 and 100000 100000, because a deploy.resources block is honoured by some Compose versions and ignored by others.

A Per-Request Figure Needs Its Rate

The same arm reads 279, 202 and 131 mJ per request at 29, 57 and 114 requests per second. The decline is the processor package leaving its idle C-states, a step that costs the same whether the window carried 300 requests or 1,100. Idle subtraction cannot remove it, because it is absent from the idle arm by definition. A per-request figure quoted without its rate is that fixed cost divided by whatever throughput the run reached.

A fixed-plus-marginal fit does not fix this. The marginal cost itself falls with rate, 123 mJ per additional request between 29 and 57 per second against 60 mJ between 57 and 114, so the curve is concave and a fitted slope describes the spacing of the rungs. Both arms are compared at the same request count instead, interpolating between measured rungs.

The Two Penalties

drupflare pays two costs that a native host does not:

  • Wasm render: 1.65 times the CPU of a native one, measured, at 32.5 ms against 19.7 ms for the same page on the same machine. At the same watts that is 153.8 mJ against 92.9 mJ per render.
  • Cached hit: 4.6 mJ against 1.9 mJ for an nginx hit, derived on one CPU basis. A view that reaches drupflare is charged the front Worker and the object, 1.8 ms of CPU, while nginx answers a hit from its own cache.

Rendering less often outweighs both up to a point the model prices. An nginx-hit opponent costs more per anonymous view than drupflare once it renders on more than 3.0% of views, because renders at that rate repay the 2.7 mJ gap on the hit. The Closest Opponent

The closest opponent is a shielded 24 h tag-purged cache, which uses 1.45 times drupflare's energy per view at a million views and 1.42 times from ten million up.   • The model has no CDN eviction term. A real cache drops cold pages under memory pressure and each location fills cold, while a page store that persists on disk does not.
  • The opponent's hit is priced as an origin nginx hit, 1.9 mJ, because no source publishes the cost of a CDN hit. Costing the hit at zero is a floor and gives 1.10 to 1.14 times.

What A Conventional Host Needs

A conventional price here is the bill for the hardware the traffic needs, and it moves with traffic. Peak load is five times the average, and every view is charged to the origin as a render. A render costs 17.9 ms of CPU, from the shipped nginx and PHP-FPM stack's measured 67 renders a second on 1.2 cores. The cores a box needs are the fewest whole cores that keep the p95 response inside a bound in an M/M/c queue, and never above a utilisation cap, at that peak rate.

Two bounds give two sizings. A viable box keeps the p95 under 60 seconds, the default read timeout of nginx and Apache [7], [27], [28], so no client or proxy gives up, with utilisation capped at 95%. Cloudflare's own cutoff is 125 seconds [29]. A matched box keeps the p95 under 0.8 seconds, the first-byte time web.dev rates good (poor starts at 1.8 seconds) [30], with utilisation capped at 80%. The caps are modelled, and the 80% matches Linode's guidance to stay below 80% sustained CPU on a shared plan [31]. A burstable plan has a lower baseline, such as the 10% of a vCPU on a t3.micro [32], but the average load here is a few percent of one core.

Memory sets the floor and does not grow with traffic. The Ubuntu 24.04 cloud image needs 1 GB of RAM for the operating system alone [33]. The shipped stack's nginx and 32 PHP-FPM children held 172 MB under the render load, and MariaDB's default InnoDB buffer pool is 128 MiB [34]. Together that is 1.3 GiB a box, so a 1 GiB plan is below the floor and 2 GiB is the smallest size that meets it. Drupal's own documentation gives 1 GB as the minimum for Composer [35], which is a build requirement and not a serving one. Disk is about 10 GB in use (the operating system, the 167 MB Drupal tree and the 5.8 MB database, modelled) against 25 GB on the smallest 2 GiB plans. Transfer is 166 KB a view, the first load of the demo site (66 requests, 17.2 KB of HTML, n=1), so 3 million views move about 498 GB. Every view is charged as a first load, and no CDN is assumed. What The Price Column Does Not Buy

A monthly price buys capacity from one place, and this page does not measure capacity beyond the sizing above. It does not buy the latency profile: the same workload measures 100.2 ms on a VPS against 8.9 ms on drupflare once an 82 ms round trip is injected, because one serves from a region and the other from the visitor's colo. It does not buy the tail either, where the VPS p50 runs from 59 ms at 4 clients to 182 ms at 96 while drupflare holds. The latency-matched column prices the first of those; nothing here prices the second.

The Shape Of The Bills

The two bills differ in shape more than in total. A conventional host charges per site per month whether or not anyone visits, and for hardware that grows with traffic; drupflare charges for traffic served, against an allowance that costs nothing until it is crossed. The comparison therefore widens with the number of idle sites and narrows with traffic. For a single site at ten million views a month drupflare costs $5.15, the $5 subscription plus $0.15 of usage, against $10.50 for the cheapest VPS, and the latency-matched host is 11.3 times dearer.

What This Does Not Claim

  • No per-tenant Cloudflare wattage. It is not observable. Probing a deployed Cloudflare Container found no energy counter by any of the six routes a Linux process has, and no energy field exists anywhere in the account's analytics schema. The Cloudflare side of every figure above is an allocation over measured workload and published hardware.
  • No claim that 1,000 sites replace 1,000 servers. VPS providers and managed platforms already consolidate, so the comparison is against hosting that has captured most of the multi-tenancy saving.
  • Conventional prices are sized list prices. They exclude labour, a CDN, the database and file replication of a multi-region origin and cross-region transfer, and they price a box from documented minimums and a measured stack. No 1 GiB or 2 GiB box was run under load for this page, and no source gives PHP-FPM memory per child for Drupal.
  • The energy worst case and the priced box differ in size. The energy model charges a VPS a 320th of a host, two vCPUs. The cost model prices one vCPU and 2 GiB, which is a 192nd of a 384 GiB host by memory, so the energy charge is at most low for the box priced.
  • Pantheon as a price, not an energy baseline. It is already multi-tenant, and how many machines it runs, how well utilised they are and how much of that would persist without a given workload are all unobservable from outside.
  • No market-share multiplier. A CMS's share of websites is a count of sites and not a quantity of compute. It changes the addressable population and transfers no measurement.
  • Incremental energy is not a hosting total. The rig produces idle-subtracted workload energy. A continuously provisioned server also pays its idle, and the equivalent allocation on a shared edge fleet cannot be measured. Operating States brackets it from zero to a memory-share bound; neither end is a reading.
  • No allocation for Cloudflare's own fleet utilisation. The 2.22 W a busy core is the full-load floor, and Watts For A Busy Core shows what a lower host load would charge. At 10,000 views that leaves the saving above 99.98% against one VPS, and it moves no per-view ratio, since both sides use the same figure.
  • No cold-encounter reading. The headline carries none, and no deployed site has reported coldOfTraffic. The sensitivity rows are assumptions about how many editor sessions find an object cold.
  • No price on the hostname lookup. A request through the production hostname resolves the site from a key-value mapping, memoised for a minute, and its CPU time has not been read. Its wall time is 4 ms warm and 46 to 140 ms in a colo that has not seen the key, and CPU time excludes the wait. The closest per-view cell has room for about 0.3 ms of extra CPU on every view against a free hit and 0.9 ms against an nginx hit, at a million views a month and above.
  • No price on the shell tier, replica lanes or the plan's compile. A logged-in view that misses the compiled plan can be answered from a stored shell, which renders a fragment instead of the page. Lanes copy writes to every object of a busy site. The plan compiles from three agreeing sessions. None has an energy class here, and How The Lead Moves charges a missed plan as a render.
  • Institutional rows use an assumed workload. The page views come from the case studies. The logged-in share, the saves a day and the pages a save invalidates are the model's, not theirs.

The first command needs a bare-metal x86 host with readable RAPL counters and a load generator on a different machine. A virtual machine cannot substitute: a Cloudflare Container exposes no energy counter at all, and a mainstream KVM guest exposes a power PMU that reads a constant zero, which a tool reports as 0 W. --ladder is required for a per-request figure. One rate cannot separate the cost of a request from the cost of the package being awake, so the two arms are read at the same request count.
