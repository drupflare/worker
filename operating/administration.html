The Admin Surfaces

Seven pages under /_cfw drive machinery that already exists, and all take the owner token; the sign-in flow is on Configuration Operations.

page path what it does
Limits /_cfw every metered resource, what spends it, and whether exceeding it bills or stops working
Extend /_cfw/extend whether a contrib module installs here, answered against the shipped lock
Commands /_cfw/commands a Drush-shaped field over the site's operations
Operate /_cfw/operate the repair actions: purge, reconcile, sweep, database updates, restart the fill chain
Deploy /_cfw/deploy the provisioning steps, two of which cannot be automated
Git /_cfw/git remotes, branches, pull requests and the working-tree diff
Access /_cfw/access the OpenID Connect provider

The Commands field takes Drush spellings and resolves them to the operation the site registers, so cache:rebuild, cache-rebuild, cc and cr are the same command. en <module> routes to the module installer and not to the operations registry, and an operation given arguments it cannot take is refused by name instead of being truncated to its first word.

cr                  rebuild the caches
en webform          install a module
en webform --dry    check whether it would install, without installing
status              generation, migration state, queue depth

An operation with no driver is listed and disabled, not hidden, because a refusal with no named alternative is a refusal that gets retried.

Extend checks a package against the shipped lock, installs it, and enables it. The page keeps those three steps separate: a check writes nothing, an install fetches the package and writes its files, and enabling turns the module on and reboots the interpreter. The same three are /installable, /install and /enable for a script.

Inside Drupal's Own Admin

/_cfw is the host's surface and sits outside Drupal. The module adds a second one where a Drupal administrator looks first:

page path what it shows
Drupflare /admin/config/drupflare the section, alongside Drupal's own configuration groups
Runtime Status /admin/config/drupflare/runtime the replica pool, page tiers, warming, edge plan and write lanes
Help /admin/help/topic/drupflare what runs where, and which Drupal assumptions do not hold here

Runtime Status reads the same payload /serve-stats returns, so the admin page and the host report cannot disagree.

Single Sign-On

The Access page at /_cfw/access sets the issuer and client id for the OpenID Connect provider the host serves at /oidc. The client secret goes in the OIDC_CLIENT_SECRET binding. The redirect URI to register with the provider is shown on the page, and saving checks the issuer's discovery document at once, so a typo surfaces there and not at someone's first login. The verification rules, the drupal/externalauth requirement and the drupal/openid_connect alternative are on OIDC Login.

URL Routing

Drupal owns the URL space. Any path the Worker does not claim is served as a page, so /, /user/login, /admin and /node/1 all work. The Worker's own surfaces live under /_cfw, which Drupal does not generate; its diagnostic and owner routes are single-segment names like /health and /export.

Which site a request resolves to is decided in src/ops/site-id.ts: a KV mapping for the host, then the SITE_ID var, then the deployment's primary site, then the hostname itself, then site. One deployment is one site, so a second domain pointed at the worker reaches the site already claimed and does not open a new one. A host mapped in KV is an alias: its pages, redirects and login cookie carry that host, and drangler domain add <host> writes the mapping and the Custom Domain route. On localhost the hostname names no site, so it lands on site. ?site= is refused on the public routes, so a link cannot choose which site answers; an owner route accepts it because the object checks the token itself, and PW_DIAGNOSTICS=1 accepts it everywhere, which is what /serve?site=X&path=Y uses.

Retiring a Site

POST /retire?site=<id> with the body {"confirm": "<id>"} removes one site from a deployment. It is an owner route answered by the Worker, with no route table entry for the object, because it edits CONFIG_KV and the fleet database. The token is the target site's own, checked in the Worker (with the same per-address failure budget as the other owner routes) and again in the object. PW_DIAGNOSTICS=1 does not open it.

The Worker refuses, before touching anything:

  • the deployment's primary, and a sole claimed site, with 409; choose another primary with PUT /deployment first
  • a body whose confirm is not the site id, with 400
  • a site that is not in the deployment's claimed list, with 409, unless the URL carries force=1

An object that was never claimed usually has no owner token. With force=1, the owner token of the deployment's primary retires it, and the audit entry names the actor as primary: plus the first eight characters of the token's hash. The object accepts that only while it holds no owner token of its own, so a claimed site, or any site with a token, is never reachable that way. A name whose object holds no tables and no alarm answers 404, so a typo does not mint an object just to wipe it.

The audit entry is written first, to the site:retired-log key in CONFIG_KV, as a hash chain in the format of the owner audit log, and is also printed with console.log. The object's own audit ring is in the storage that the wipe deletes, so it cannot hold the entry. A refused or failed wipe adds a second entry carrying the failing status.

The object then deletes its alarm and all of its storage, drops its interpreter and any retained one, and answers 410 to every later request while that instance is resident. Its alarm and fill scheduling do nothing from then on. After the instance is evicted the name is an empty object: a request that reaches the host provisions a new site under it. Remove the host mapping, or the route, to stop that.

The Worker then removes the site from the claimed list in the deployment document, deletes its cfw_fleet row so the scheduled warm window stops driving it, and deletes every site:host:<host> key that points at it. A failure in any of those three is reported under warnings in the answer, and the wipe stands.
